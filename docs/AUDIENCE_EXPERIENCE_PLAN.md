# Executive and technical learning plan

## Goal
A leader can explain APS and frame an accountable evaluation; an engineer can explain a boundary, inspect its effects, and locate reproducible evidence. Browser models and frozen experiments remain distinct.

## Implementation
1. Replace category navigation with reader questions; introduce APS before HAZOP.
2. Explain one purchasing story, then offer three narrated failure examples and isolated A/B/C comparisons using the existing workflow engine, identical inputs and schedule. Never replace the active run implicitly.
3. Translate mechanisms into business commitments and show capability scope.
4. Add an editable, printable leadership brief derived from current observations, with unassigned ownership, proposed metrics and open evidence needs. No approval or persistence implied.
5. Add technical orientation, model comparison, trust/enforcement boundaries, a worked HAZOP chain and precise control contracts with pinned source/test references.
6. Coordinate event, message, commitment and invariant inspection; show state-version transitions without inventing historical snapshots.
7. Explain frozen experiment claims and reproduction separately from browser replay. Keep all original evidence and verifier gates.

## Validation
Run readiness, root tests/typecheck and frontend lint/typecheck/tests/build/static/fixture/production checks. Add behavioral tests for comparison isolation, bounded recovery, leadership brief truthfulness, and technical inspection. Update browser checks for intentional navigation changes and exercise new learning surfaces. Review desktop/mobile and both themes. Record actual results in the PR.

## Human validation (pending, not simulated)
Recruit 5–8 unfamiliar executive readers and 5–8 engineers through the project owner. No recruitment or messages sent by this implementation.
- Executive: explain APS in one minute; distinguish analysis, enforcement and assurance; explain two safeguards; name an owner and unresolved decision; state evidence limits.
- Engineer: identify the three models; locate enforcement and its assumptions; trace a failed property to source/test; reproduce a supported behavior; identify a remaining limitation.
- Proposed formative target: at least four of five in each audience complete these tasks unaided. Record misunderstandings and task time, revise, then retest affected tasks. This is a usability target, not safety validation.

## Scope
No policy, simulator algorithm, frozen evidence, dependency, CI workflow, risk rating or human signoff changes. Live integrations, distributed atomicity, objective arbitration, measured ROI and independent assurance remain outside the demonstrated capabilities.
